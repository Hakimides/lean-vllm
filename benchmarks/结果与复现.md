# 五阶段基线与结果

一次跑完：**5 个阶段 × 2 个运行点 × 3 个种子 × 正反两遍 = 60 发**，
全部 `warmup.ramp.stable = true`。同一台机器、同一套测量代码（阶段一用它当时的提交 `1455a53`）。

**一句话结论**：五个阶段里真正有效的是三处（混合批、fp8 KV、prefill 进图）。
**最优组合是阶段五** —— 相对最初的引擎，λ=4.0 吞吐 **+57.6%**、TTFT p50 **−97.4%**、实际耗时 **−36.5%**；
λ=1.0 TTFT p50 **−78.9%**、ITL p99 **−76.2%**；而精度只付 **+0.51%**。

---

## 一、五个阶段分别是什么组合

| 阶段 | 组合 | 关键开关 | 提交 |
|---|---|---|---|
| **一** | 上游极简引擎 + 自建测量设施（**无混合批、无量化、无图**） | — | `1455a53` |
| **二** | + **混合批**（调度改成 decode 优先排、收请求前留 10% KV 余量、每步 prefill 上限 1024） | — | `2396566`…`eb2dd53` |
| **三** | + **fp8 权重量化**（W8A8，per-tensor 静态 scale）；KV 仍 bf16、图关 | `--fp8-linear` | `9480c80` |
| **四** | + **fp8 KV 量化**（写入时量化，容量 ×2）；权重仍 bf16、图关 | `--kv-fp8` | `ec1ae53` |
| **五** | + **prefill 进图**（含 prefill 的步按 token 桶捕进 CUDA graph） | `--kv-fp8` | `7510e0a` |
| 附 | **全开**（权重 fp8 + KV fp8 + 进图）——更快，但精度不可接受 | `--fp8-linear --kv-fp8` | — |

> **阶段三与四是并列的两条路，不是累加**：三 = 权重 fp8 / KV bf16，四 = KV fp8 / 权重 bf16。
> 所以**四的对照是二**（不是三），**五的对照是四**。
> 另外「混合批」没有开关，内嵌在调度器中，所以阶段二~五都带着它，只有阶段一没有。

## 二、怎么测的

| 项 | 值 |
|---|---|
| 运行点 | **λ=1.0**（干净点）与 **λ=4.0**（饱和点） |
| 负载 | n=256 条泊松到达，长度按 4 种形状抽（合成负载，随机 token） |
| 种子 | 0 / 1 / 2 |
| GPU 暖机 | 每发 45 s（含在判稳检查里） |
| 仪器 | `--gpu-sample-s 0`（关运行中采样，冻结仪器） |
| 交错 | 每个 λ 跑**回文序**（正序一遍 + 反序一遍），抵消会话内单调漂移 |
| 判读门槛 | ITL p50 ≈1%、ITL p99 ≈2%、TTFT p50 ≈5%（同种子才能比） |
| 完整规范 | 见 [`测试标准.md`](测试标准.md) |
| 原始数据 | 逐请求/逐步明细（约 380 MB，硬件绑定）留在本地，未入库 |

### 一条测量观察：顺序倾向

同一种子连跑两次（原始数据共 6 组）时，**prefill 步耗时驱动的指标上有"后跑偏高"的倾向**：

```
prefill p50   6/6 后跑更高
实际耗时       6/6 后跑更高
TTFT p50      5/6
ITL max       5/6
ITL p99       3/6   ← 这一项没有稳定方向
```

幅度多数在 0~2%，但**尾部很重**（个别组到 8%~24%）。

**含义**：这类倾向不会被"同种子重跑"消除，所以对比协议要求**反序交错**（正反各一次把它均摊掉，
见 `测试标准.md` §6）。

⚠️ 这是**观察，不是规律**：① 幅度不稳定，② 反序只能抵消一阶漂移，**单次离群值救不了**
（所以拿到数据后仍要看组内重复性、并检查 `warmup.ramp.stable`）。

## 三、各阶段结果与评价

每张表的「Δ vs 父」= 该阶段相对**它上一跳**的变化率；「值」= 3 种子中位、正反两遍合并。
**Δ% 的定义：先算每个种子自己的变化率，再取三种子的中位**（所以「1,006 → 1,611」标 +57.6%，
不是两个中位直接相除的 +60%——两种统计量的差别来自各种子负载本身不同）。

### 阶段一 · 基础引擎 + 测量设施

**组合**：上游极简引擎 + 自建测量设施。无混合批、无量化、无 CUDA 图。

|---|---|---|
| TTFT p50 (ms) | 67.22 | 35,831 |
| prefill p50 (ms) | 67.19 | 102.7 |
| ITL p50 (ms) | 12.61 | 25.26 |
| ITL p99 (ms) | 64.75 | 143.0 |
| ITL max (ms) | 341.2 | 7,560 |
| E2E p99 (ms) | 22,257 | 92,925 |
| 输出吞吐 (tok/s) | 574.6 | 1,006 |
| 抢占次数 | 0 | **83** |
| 重算 token | 0 | **37,634** |
| 最大并发 | 18.0 | 45.0 |
| 队列最深 | 0 | 141 |
| 实际耗时 (s) | 265.7 | 150.7 |

所以 λ=4.0 上出现 83 次抢占、37,634 token 重算、ITL max 达 7.5 秒。**后面四个阶段都在修这个。**

**结论：这条路的正确写法是"试过、被数据否掉"。**

代价只有一处：padding 会改变 GEMM 的 M，约 **10% 的进图 prefill 步会翻一个 token**（其余完全相同）。

## 四、精度（端到端实测，非模拟）

走引擎真实路径、teacher forcing、6 段文本、只统计纯 decode 步的预测：

| 组合 | PPL 均值变化 | 中位 | 业内口径（见下） |
|---|---|---|---|
| bf16 | 0 | — | — |
| **只 KV（= 阶段四/五）** | **+0.51%** | +0.15% | ✅ 可接受 |
| 只权重（= 阶段三） | +3.82% | +1.84% | ⚠️ 偏高 |
| 全开 | +6.45% | +2.80% | ❌ 不可接受 |

**业内口径**（FP8 属于生产默认方案）：
- **FP8 KV**：接近无损，推理类任务上通常 **1~2 分以内**，且推荐 per-head 而非 per-tensor scaling；
  4-bit KV 才明显掉点（64K+ 上下文掉 3~5 分）。
- **FP8 W8A8 权重**：ACL 2025 一篇 50 万+ 次评测的结论是 **"lossless across all model scales"**（朴素 RTN、免校准）。
- 口径是**任务精度**（MMLU/GPQA 的分），与 PPL 不能直接换算。

**据此判断**：KV（+0.51%）**在业内区间内**；而权重与全开**明显偏高**——
但差距在量化方案的档位，不在 FP8 本身。

我们的方案是 per-tensor 标量 scale + 静态校准。这个档位是被实测约束定下来的：
row-wise scale 在 CUDA graph 下不可用，动态量化在 eager 下被 CPU 派发开销耗尽，
两条都堵住，才退到标量 per-tensor。校准集的敏感性也量过：换四段不同文本，代价在 +2.89% ~ +4.61% 之间。
所以 +3.82% 反映的是"在这套约束下能做到的水平"，不是 FP8 的固有代价。



## 五、总结与最优组合

**三处有效优化的贡献**（λ=4.0，相对各自父阶段）：

| 优化 | 吞吐 | 关键延迟 | 精度代价 |
|---|---|---|---|
| **混合批**（二 vs 一） | −0.1% | ITL p99 **−44.3%**、抢占 83→1、重算 −99% | 0 |
| **fp8 KV**（四 vs 二） | **+55.3%** | 队列 −60.6%、耗时 −35.6%、TTFT −92.2% | **+0.51%** |
| **prefill 进图**（五 vs 四） | +2.2% | TTFT p50 **−68.1%**（λ=1.0 上 −81.1%）、ITL p99 −74.6% | ≈0 |
| ~~fp8 权重~~（三 vs 二） | +8.2% | ITL p50 −11.0% | **+3.82%** ❌ 被否 |

**最优组合 = 阶段五 = 混合批 + fp8 KV + prefill 进图（权重保持 bf16）**

相对最初的引擎（阶段一）：
- **λ=4.0**：吞吐 1,006 → **1,611 tok/s（+57.6%）**、TTFT p50 35,831 → **932 ms（−97.4%）**、
  实际耗时 150.7 → **96.0 s（−36.5%）**、抢占 83 → **0**、重算 37,634 → **0**
- **λ=1.0**：TTFT p50 67.2 → **14.2 ms（−78.9%）**、ITL p50 −31.7%、ITL p99 **−76.2%**、E2E p99 −33.6%
- **精度**：只付 **+0.51%**（中位 +0.15%），在业内可接受区间内

**不要选的两个**：
- **只权重 fp8**：精度 +3.82% 换来 +8.2% 吞吐，并在三个维度上全面劣于 KV fp8 → 不划算
- **全开**（权重 + KV + 进图）：吞吐最高（1,797 tok/s，比不量化的阶段二 **+78.8%**），但精度 **+6.45%**，
  超出可接受区间 → 只能用于不在乎精度的场景

**一个额外的发现**：进图之后，两种量化的吞吐收益**变成可加的**了
（λ=4.0 上 权重 ×1.105、KV ×1.590，相乘 = 1.757，而实测 1,797/1,013 = **1.774**）。
也就是说"两种量化不叠加"这条结论**只对 prefill 还走 eager 的旧制度成立**。

## 六、怎么复现

运行点固定 **λ=1.0 / λ=4.0**、`--n 256`、3 个种子。tag 约定 `bl_s{阶段}_l{λ}`。

| 阶段 | 跑法 |
|---|---|
| 一 | `git checkout 1455a53`，用**那个提交里的** `benchmarks/sweep.py` 跑（那时的测量代码还没有 `--kv-fp8` 等开关） |
| 二 | 最新代码，开关全关 |
| 三 | 最新代码，`--fp8-linear --no-prefill-graph` |
| 四 | 最新代码，`--kv-fp8 --no-prefill-graph` |
| 五 | 最新代码，`--kv-fp8`（prefill 图默认开） |

```bash
python -m benchmarks.sweep --tag bl_s5_l1 --seeds 0 1 2 --repeats 1 --n 256 --lam 1.0 --kv-fp8
```

**每个 λ 建议跑回文序**（正序一遍 + 反序一遍，tag 加 `b` 区分），以抵消会话内单调漂移：
`五 四 三 二 一 一 二 三 四 五`。阶段一那两发在正中间相邻，只需一次 `checkout` 窗口。

**跑完必须看 `warmup.ramp.stable` 是否为 `true`**，为 `false` 就调大 `--warmup-gpu-s` 重跑那一发。
