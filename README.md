# lean-vllm

在一张 **8 GB 消费级显卡**上，为一个极简 LLM 推理引擎做**测量与优化**的实验。

> 引擎本体基于一个极简的开源参考实现。**本项目的产出不是引擎本身**，而是：
> 一套可复现的测量方法、三处落地的优化、以及一处在数据面前被否掉的方案。

## 结果

相对优化前的引擎；同一台机器、同一套测量代码、3 个种子**交错对照**（方法见 `benchmarks/测试标准.md`）。

| | λ=4.0（饱和点） | λ=1.0（干净点） |
|---|---|---|
| 输出吞吐 | 1,006 → **1,611 tok/s（+57.6%）** | 575 → 576（+0.3%） |
| TTFT p50 | 35,831 → **932 ms（−97.4%）** | 67.2 → **14.2 ms（−78.9%）** |
| ITL p99 | 143 → 112 ms（−21.8%） | 64.8 → **15.4 ms（−76.2%）** |
| 实际耗时 | 150.7 → **96.0 s（−36.5%）** | 265.7 → 264.9 s |
| 抢占 / 重算 | 83 次 / 37,634 token → **0 / 0** | 0 / 0 |
| 精度（PPL，端到端实测） | — | **+0.51%** |

完整的两两对照表（每个阶段 vs 上一阶段 / vs 最初）见 [`benchmarks/结果与复现.md`](benchmarks/结果与复现.md)。

## 一、硬件约束决定了一切

| 项 | 值 |
|---|---|
| GPU | RTX 4060 Laptop，**8 GB**，sm_89，24 SM |
| 显存带宽 | 标称 256 GB/s（实测 decode 步贴着约 229 GB/s 跑） |
| 主机 | 16 GB **单通道** DDR5 |
| 模型 | Qwen3-0.6B（bf16） |

**KV 每 token = 2 × 28 层 × 8 个 KV 头 × 128 head_dim × 2 B = 112 KiB。**

于是 8 GB 显存下 bf16 的 KV 池只能装 **41,728 token**。这个数字是本项目**所有瓶颈的根源**：
引擎的吞吐上限、抢占次数、队首阻塞、TTFT 的长尾——全部由"KV 装不下更多并发"决定。
**后面每一个优化，本质上都是在和这 41,728 个 token 较劲。**

## 二、五个阶段

| 阶段 | 改了什么 | 关键数字（相对上一阶段） | 状态 |
|---|---|---|---|
| 一 | 基础引擎 + **自建测量设施**（补上游缺的延迟测量） | 参照系：λ=4.0 抢占 83 次、重算 37,634、ITL max **7.5 s** | 基线 |
| 二 | **混合批**：调度改成 decode 优先排、收请求前留 10% KV 余量、每步 prefill 上限 | λ=4.0 ITL p99 **−44.3%**、抢占 83→1、重算 **−99%**，吞吐 −0.1% | 落地 |
| 三 | **fp8 权重量化**（W8A8） | λ=4.0 吞吐 +8.2%、ITL p50 −11.0%；**精度 +3.82%** | **被否** |
| 四 | **fp8 KV 量化**（写入时量化，容量 ×2） | λ=4.0 吞吐 **+55.3%**、队列 −60.6%、耗时 −35.6%；精度 +0.51% | 落地 |
| 五 | **prefill 进 CUDA graph**（含 prefill 的步按 token 桶捕获） | λ=1.0 TTFT **−81.1%**、ITL p99 **−74.6%**；λ=4.0 吞吐 +2.2%；精度 ≈0 | 落地 |

> 阶段三与阶段四是**并列的两条路**（三 = 权重 fp8/KV bf16，四 = KV fp8/权重 bf16），不是累加。
> 阶段五建立在阶段四之上。

## 三、三处落地的优化

### 1 · 混合批：改调度，让 prefill 不再阻塞 decode

**问题**：上游调度器让 prefill **绝对优先** —— 只要这一步排上了任何 prefill，整步就只有 prefill，
**所有在跑的序列一个字都生成不出来**。一条长 prompt 就能让整个引擎停摆，这是 ITL max 达 **7.5 秒**的来源。

**改法**：先排 decode，再用剩余预算排 prefill（于是同一步可以同时含两者）；收新请求前留出 10% 空闲 KV 页
作为准入余量；给每步的 prefill token 数加上限。

**效果**：λ=4.0 上 ITL p99 **143 → 79.9 ms（−44.3%）**、抢占 **83 → 1 次**、重算 **−99%**，
而**吞吐只差 0.1%**。
**代价**：λ=1.0 的 TTFT +7.3% —— 长 prompt 被分块，每块要重付一次固定开销。**用首字延迟换尾部延迟。**

### 2 · fp8 KV 量化：把 KV 容量翻倍

**问题**：KV 池大小就是吞吐上限（见第一节）。bf16 下 41,728 token 已经到顶。

**改法**：KV 池改用 fp8 存储，**写入时量化**；attention 从 KV 池读 fp8。为此移植了三个 Triton attention kernel
（decode / unified / helpers，逐字复制、保留 Apache-2.0 署名）。

**效果**：**KV 容量 41,728 → 83,456 token（×2）**；λ=4.0 吞吐 **1,006 → 1,577 tok/s（+55.3%）**、
队列最深 141 → 53、实际耗时 150.7 → 97.9 s；重算与抢占**归零**。
**代价**：λ=4.0 的 ITL p99 **+39.2%** —— 但这不是 kernel 变慢，而是**工作点上移**（并发 45 → 65，
每步要读更多 KV），可以用准入余量调回；以及精度 **+0.51%**。

### 3 · prefill 进 CUDA graph：消除 CPU 派发下限

**问题**：含 prefill 的步走 eager，一步要发约 **640 个 kernel**；按每个约 **88 µs** 的 CPU 派发开销算，
这是一条约 **56 ms 的下限** —— 而这一步的 GPU 只干约 15 ms。**GPU 一直在等 CPU。**

**改法**：把形状对齐到 token 桶（{128, 256, 512, 1024}），每个桶捕获一张 CUDA graph；
多出来的 batch 位用"长度 0 的序列"补（kernel 会早退），`slot_mapping` 空位填 −1。

**效果**：λ=1.0 的 TTFT p50 **75.7 → 14.2 ms（−81.1%）**、ITL p99 **−74.6%**；
λ=4.0 吞吐 +2.2%、队列 −13.2%。**吞吐零代价。**
**代价**：padding 会改变 GEMM 的 M，于是 bf16 舍入变化、再被 fp8 KV 的粗量化放大 ——
约 **10% 的进图 prefill 步会翻一个 token**，其余完全相同（40 步 logits 对照：21 步 bit 级相同、36 步 top-1 相同）。

## 四、被数据否掉的方向

| 方向 | 为什么否掉 |
|---|---|
| **fp8 权重量化** | **fp8 KV 在三个维度上全面占优**：精度差 6.5 倍（+3.82% vs +0.51%）、吞吐差 6 倍（+8.2% vs +55.3%）、**且不扩容**（KV 页 41,728 → 40,960，反而 −1.8%）。正确写法是"试过、被数据否掉" |
| 投机解码 | `ngram`/`suffix` 靠上下文重复，而**负载是随机 token，永不命中**；`draft_model` 需要更小的同族模型（0.6B 已是最小） |
| 前缀缓存调优 | 合成负载是随机 token，命中率**恒为 0** |
| P/D 解耦 | 单卡 8 GB |
| 自己写 Triton 量化 kernel | 实测启动开销 76~91 µs，小 M 时压不到需要的水平 |
| INT4 KV | 能再翻倍容量，但要再移植一个 kernel，且精度风险大 |

## 五、精度

端到端实测（走引擎真实路径、teacher forcing、6 段文本、只统计纯 decode 步的预测）：

| 组合 | PPL 变化（均值 / 中位） | 业内口径 |
|---|---|---|
| bf16 | 0 | — |
| **只 KV（本项目采用）** | **+0.51% / +0.15%** | ✅ 可接受（fp8 KV 是生产默认方案，通常 1~2 分以内） |
| 只权重 | +3.82% / +1.84% | ⚠️ 显著高于业内 |
| 两样都开 | +6.45% / +2.80% | ❌ 不可接受 |

**PPL 涨幅来自量化方案的粒度，不是 fp8 的固有代价**：本项目用 per-tensor 静态 scale + 单段校准文本；
这一档位是被实测约束定下来的 —— row-wise scale 在 CUDA graph 下不可用、动态量化在 eager 下被 CPU 派发耗尽，
两条都堵住才退到标量 per-tensor。

## 七、这个项目的边界（没有验证什么）

1. **张量并行从未跑过** —— 碍于硬件限制，只在单卡上测过
2. **负载是合成的**（随机 token、4 种长度形状），不是真实流量分布
3. 历史基线未必能在今天复刻（跨会话漂移真实存在），
   所以本文所有数字都来自**同一批次连续跑完的对照**，而不是历史记录的拼接
